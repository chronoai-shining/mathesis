# Hexagon 调研与 Mathesis 产品建议

调研日期：2026-10-13。Mathesis 对照版本：`09562d157e521d1e655dd0997b1f52ca26bf3b95`。

本文是产品调研和建议，不修改当前公开规则、作者权限或审稿流程。竞品结论来自公开官网、API 文档、实际记录和官方反馈；没有登录投稿或实测其内部处理。Mathesis 的“已有”指仓库实现与契约，不能代替生产端到端可用性验证。

## 判断

Mathesis 的定位可以是：**发布数学研究，并获得审稿、修订与形式化验证服务。** 论文、短文和猜想构成内容入口；审稿是首要服务；CMA 承担持续的研究执行；形式化交付可以复验的证据。

Hexagon 已把基础存档做得相当完整。我们应补齐研究发现和学术引用的基本体验，同时把主要投入放在它明确不提供的审稿，以及从问题发现到修订和独立验证的完整交付。不要把“有 API”“有 MCP”“可链接 Lean”当作独占优势。

## Hexagon 已核实的能力

1. **收录范围和定位。** 官网收录数学科学与理论计算机科学的研究作品，包括原创和阐释性作品。接受人工或 AI 生成的文本；投稿人仍需善意相信作品正确、有社区价值并努力准确引用。允许与 arXiv 同时发布。[H1][H2]
2. **不做同行评审。** 官网明确声明不进行 peer review。自动检查编译、学科范围和不当内容，beta 阶段另有人类 moderator 检查；不会以重要性、新颖性或正确性为拒绝理由。收录不构成对正确性、质量或新颖性的判断。[H1][H2]
3. **存档基础。** 每个公开版本有稳定永久标识，撤回后保留带通知的记录；支持 TeX、PDF、源码下载和源码树、版本历史、BibTeX、许可证选择、ORCID 关联。实际记录公开展示这些字段。[H2][H4]
4. **检索。** 官网有标题、贡献者、摘要、标识、MSC2020、学科、文本来源、人类理解程度和形式化链接筛选。JSON API 另有工具、标签等过滤。[H3][H5]
5. **自动化。** 提供 arXiv 风格的 Atom 查询、JSON API、只读 MCP；投稿 API 支持受限凭证、幂等、分片上传、恢复、编译预览及日志。批量投稿反馈已被维护者标记完成；不能误写为未来功能。[H5][H6]
6. **形式化。** 官网明确不接受 Lean 等代码作为投稿组成部分，允许链接 Mathlib、Palomar、Prove2.me、Tau Ceti。外部形式化链接可作为记录级注释更新，不等同于本平台独立复验某个版本的定理。[H2][H5]
7. **DOI。** 官网仍把 DOI 列为未来功能；抽查的 `2609.00104v1` 显示“Not assigned”。不能由一条样本推断每条记录均无 DOI，更不能写成已具备普遍 DOI 发放服务。[H2][H4]
8. **社区基础。** 由 Hexagon Mathematics Foundation 运营，Benjamin Antieau 为 Executive Director；董事和顾问名单体现了较强学术网络。Terence Tao 博客刊载了 Antieau 的客座介绍，不能据此称 Tao 为创始人或董事。[H7][H8][H9]

公开反馈中，HTML/MathML 阅读、版本级 stewardship resources 和更细的计算用量元数据仍为 open。资源提案提到 verification certificates，但本次未从公开 API、抽查记录和官网规则核实出正在交付的完整证书服务，不能据此称其已提供审稿，也不能断言不存在任何第三方验证功能。[H10][H11][H12]

## 与 Mathesis 的对照

| 能力 | Hexagon 公开证据 | Mathesis 当前仓库 | 建议 |
|---|---|---|---|
| 学术存档与发现 | 高级检索、分类、版本标识、源码树、BibTeX、ORCID、许可证 | 记录、PDF、版本、MSC 和作者 ORCID 字段；论文接口仅 `limit/before`；暂无同等检索和许可证选择体验 | 补齐标题/作者/摘要/MSC 检索、分类、BibTeX 和版本链接；ORCID 字段不等于认证绑定 |
| 实质审稿 | 明确不做同行评审 | GPT Pro 阅读，CMA Codex 对照源码审计，逐命题结果、疑点、文献和反馈信 | 做成作者可以直接购买或使用的独立服务，输出可核对的报告 |
| 审稿后修订 | 未核实一体化执行服务 | 有建议、版本修订和重审基础；不是完整的作者交互式修订工作台 | 把报告问题变成可执行任务，产出修改差异和逐项回应 |
| 形式化 | 外部成果链接，不接收代码 | 作者确认目标摘要、忠实性检查、独立 verifier、标准公理检查和证明回执 | 按定理交付可下载、可重建的验证包，明确覆盖范围 |
| 猜想 | 广泛收录研究作品；未核实独立猜想状态闭环 | 独立猜想和论文开放问题、作者确认目标、证明/反证、已验答案 | 把定义、已知进展、解决状态与版本化证据串起来 |
| CMA | 未发现等价作者研究工作台 | 作者自带账户/已有 workspace、指定 profile、任务恢复、付款方历史 | 用户看到“运行检查、修复问题、尝试形式化”，高级设置再展示 CMA |
| API 与代理 | 读 API、写 API、只读 MCP、批量自动投稿 | REST、贡献 CLI/MCP、代理认领与提交尝试 | 优势应是执行并返回受检验成果；保持现有接口兼容 |
| 公开可信度 | 公开声明、人类理解标记、外部链接；存档不背书 | 审稿/审计/信件私有；公开展示指定数学内容与合规验证成果 | 若增加公开审稿摘要，需新的作者同意及公开投影契约；不泄露私有报告 |

## 最重要的服务：可执行、可复核的审稿

作者提交一次，应拿到四件东西：

- **命题清单与覆盖范围**：审核了哪条命题、哪个版本、哪些部分没能核查。命题确认已有实现，可继续成为统一入口。
- **有位置和证据的问题清单**：缺失假设、证明跳步、边界反例、文献遗漏；每项定位到定理/页码/源码片段，附推导、来源或可复现计算。当前 concern 有 claim/severity/issue，精确定位与结构化证据仍需补充。
- **修改计划与逐项回复**：严重程度、建议修复、是否已解决；修订后重新核查受影响的命题。不能只给一个接受/拒绝分数。
- **可带走的报告**：固定稿件版本的 PDF/Markdown/JSON，方便作者修改、给合作者看或用于后续投稿。不得把模型意见包装成人类专家同行评审。

优先增加“只审稿、暂不公开”入口，让已经放在 arXiv 或 Hexagon 的作者也能获得帮助；由作者授权上传或合法取得相应版本的材料，保留外部来源标识。现有私有提交/不公开选项可复用，但独立服务任务、外部版本绑定、报告导出和结果展示需要明确产品设计。

GPT Pro 与 Codex 的两阶段设计有价值，但两次模型判断可能存在相关错误。竞争力要靠可查证的文献、计算和人工复核样本支撑，不能把它宣传成统计独立双审或正确性保证。

## 形式化：交付证据，而不只是生成 Lean

建议每次形式化交付包括：原文命题与版本、确认后的 Lean 目标、语义对应说明、证明源码、精确 Lean/Mathlib 版本、目标和证明摘要、使用的公理、验证回执、复验命令、仍未覆盖的假设或定理。

当前“目标忠实性检查 + 作者确认 + 独立编译/公理验证”的组合是很好的基础。需要继续区分：目标已生成、作者已确认、证明已通过、整篇论文哪些命题尚未覆盖。某一条定理成功不能变成整篇论文“已验证”。

目前接受后的 private Lean probe 只向作者投影有限结果，不直接交付完整证明包。它不能自动宣传成全功能形式化服务。建议先开放可评估的小范围定理服务：先给出可行性与缺失库清单，作者选择范围，再执行；保留当前唯一的 target/attempt/verifier 通路，不新造第二套证明验收入口。

## CMA：从账户连接变成作者研究工作台

CMA 的价值是持续执行研究任务。作者可以从一条审稿意见启动“检查这个边界情况”“修复缺失假设”“尝试形式化这个引理”，在同一版本背景下得到代码、结果和修订草稿。

每项任务显示范围、资源预算、运行状态、结果文件、验证结果和停止原因。作者应先看到任务和交付物；模型、workspace、profile 和账户连接放到高级设置。

复用现有作者账户绑定、任务持久化、恢复、凭证隔离和付款方记录。当前工作流按步骤创建专用 agent/conversation，还没有证据表明完整的持续交互工作台已经实现。CMA v2 的受限委托凭证和 NyxID 用量回执缺口已在仓库记载；不能把估算 tokens 当实收费用，不应为了 Mathesis 产品体验自行修改 CMA 上游接口。

## 存档与审稿的关键产品取舍

目前 Mathesis 的公开记录要求至少有一项审计认可的新内容/开放问题解决，或通过审核的新猜想。未接受稿件私有，形式化探测主要在接受后运行。这个契约比一般预印本存档更窄。

若目标是承担 arXiv 式存档，建议将三件事在产品模型中分开：

1. **存档与公开**：身份、权限、范围、基本规范、许可和版本保存。
2. **审稿服务**：哪些数学主张被检查、哪些问题被发现、哪些尚不确定。
3. **验证成果**：哪些具体目标有可复验的证明或反例。

这样可以收录已有结果的新证明、解释性文章和阶段性研究，而不把所有收录都解释为通过创新性审稿。此项是建议的政策/领域模型演进，尚未授权或实施；公开审稿也不能绕过当前作者/编辑私有边界。

短期可以保留当前出版门槛，先提供独立的私有审稿入口，实证服务价值，再决定扩大存档范围。永久学术档案与作者当前可切换数学详情为私有的规则也要明确取舍，不能在没有保全与权利政策时承诺完全等同 arXiv 的永久公开。

## 建议顺序与验收标准

| 优先级 | 工作 | 交付与验收 |
|---|---|---|
| P0 | 将现有审稿做成完整服务 | 一个真实稿件版本完成提交、命题确认、报告、逐项问题、作者反馈；可导出；失败可恢复。先验证至少数类不同领域和失败案例，再对外承诺时效 |
| P0 | 补齐发现与引用 | 全库标题/作者/摘要/MSC 检索，类型过滤，版本链接，BibTeX；不是仅过滤当前分页 |
| P1 | 形式化服务 | 至少一个作者确认的目标，经独立 verifier 通过，可由他人在固定环境复验；未覆盖部分明确可见 |
| P1 | CMA 执行修订任务 | 从具体审稿问题启动任务，产出修改差异、证据和复查结果；不自动公开或覆盖作者原稿 |
| P2 | 外部作品服务与猜想网络 | arXiv/Hexagon 来源与版本绑定、经授权的研究材料、引用和解答关系；读接口优先，写外部平台需单独授权 |
| P2 | 存档/审稿分层及可信展示 | 先决定收录政策、许可证、永久保存和报告公开边界，再调整公开状态与界面 |

建议先用一批有已知问题和专家结论的授权样稿做评估，按缺陷发现 precision/recall、每稿误报、作者采纳率、首次可用反馈时间、完整报告时延、任务成本、复验通过率衡量。不能用接受率、tokens 数、AI 生成评语长度或自动化任务数代替服务质量。

## 首页如何表达

保留“数学论文、短文与猜想”的清晰内容定位。增加简短服务说明：“Publish your research. Get a detailed review. Build a checked proof.”

阅读者仍优先看到检索和最新研究；作者有“提交研究 / 请求审稿”。审稿、形式化、研究工作台可以有服务说明页，说明输入、交付物、覆盖范围和预计资源。不要把后台六步流程和 CMA 配置重新堆到首屏。

当前建议入口文案必须与功能上线同步：未具备独立私有审稿产品前，不放无法完成的“请求审稿”按钮；未有真实时延数据前，不承诺“24 小时”“全自动验证整篇论文”。
